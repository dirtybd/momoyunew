2. **沙箱依赖确实缺失**：公司默认 Python 3.12 没有 docx/openpyxl/pypdf，临时 uv 安装又报跨挂载重命名错误 `Invalid cross-device link`。已一次性离线准备此 Agent 私有 Home venv，Apply 后在全新会话验证并真实处理文件。没有改系统 Python。旧 config_note 错写 Python 3.13、LibreOffice 已可用，已替换为当前实测说明。

## 模型能力与尚未证明的原因

公司模型配置声明tool_call及流式工具调用可用，原生structured_output_support=not_supported。办公节点声明三个结构化字段，不能仅依据这个能力标记就认定它导致504；Dify可能通过最终工具或文字协议兼容。模型配置上下文256000，参数规则max_tokens默认512，也不足以证明实际请求的生成上限。

单独把办公Agent输出上限改为4096进行对照，文件任务仍超时；该实验设置已恢复为原值，未修改公司共享模型配置。调整Skill后的一次完整文件Agent测试也仍超时。因此，读取限长和提示调整尚不能作为“已修复所有Agent超时”的证据。

最终回复规范修正后，无文件诊断已在6.520秒直接完成且无工具调用；完整文件路径再次测试仍超过100秒客户端诊断期限，被本地中止等待。这一结果不能用无文件成功替代完整文件能力验收。对照运行4b9ce65a-536f-42fb-8899-bf87de12ea78和05ac2dda-9c8e-4347-8e5e-808ee42a33a2的服务端日志最终仍显示工具结果后等待约180秒，分别对应调整Skill和输出上限实验。

进一步平台排查应关联上述workflow_run_id、Agent run元数据和模型网关请求日志，核对工具结果回传后的请求是否到达模型、首字节/结束标记、工具消息兼容与180秒读超时。网站端没有模型网关服务配置或服务器运行日志，不能声称已修复其内部故障。
