# 互助积分、难度与名额

## 规则

- 新需求的悬赏为1～5整数，默认1。求助人在发布前自行选择，尚未接取可经确认修改，接取后锁定。官方悬赏同规则，公告不产生积分。
- 平台发放型站内积分，不扣发布者余额。提交成果不发分，退回修改不发分，求助人确认最新版本验收完成时才一次性发给接取者。难度不是奖励乘数。
- 求助人可退回并填写反馈，接取者修改后重提，版本及反馈均保留。完成的员工卡可下架或恢复，交付材料与已发积分保留；接取者只能查看原协作记录，不能恢复发布者下架的卡片。
- 每人同时发布最多5个需求、接取最多3个。草稿和公告不计，进行中、待验收和退回修改占名额；完成后释放，未接取需求下架也释放发布名额。管理员和官方悬赏同受约束。名额在发布/接取/恢复的数据库事务内复核，并发提交不能越界。
- 个人推荐负载设置仍可更严格，模型候选会再按平台3项硬上限过滤；手动接取上限固定3。

## 难度

确认发布后异步调用Dify工作流，严格返回1～5整数与200字内依据。1单一明确的日常步骤，2常用工具整理，3专业知识或多步骤，4跨技能复杂分析和调试，5高复杂跨域多阶段。不得按奖励金额、字数或紧急程度机械评分。

评分只传任务的标题、问题、目标、交付、验收、限制、技能及期限，不传员工档案、私聊、附件内容或悬赏金额。结果记录在task_difficulty。流程失败保留pending并退避重试，不伪造分数；未配置显示unavailable。改动工作内容会失效旧评分，单改奖励不重复调用；返回后复核任务内容哈希和公开状态，旧结果不能覆盖新任务。

复用现有DIFY_MATCHING_BASE_URL/DIFY_MATCHING_API_KEY，不创建新凭证。工作流新增可选difficulty_json，匹配仍使用snapshot_json，文字审核仍使用review_json，三者恰好一个非空。难度分支返回difficulty_result_json，其余两个输出合同保持。原生流程归档见dify-workflows/matching-ui与dify-matching-workflow.yml。

后台难度与匹配串行唤醒，活动对话期间不启动新的后台调用；任务和租约可跨重启恢复。当前已有运行中的模型请求不因切页或新对话被强行重复执行。页面在可见公屏/详情存在pending时静默刷新，完成或离开后停止。

## 排行与存储

积分流水task_points以request_id为唯一键，与验收状态、提交decision在同一事务提交，重复点击、过期提交或失败回滚不会重复给分。care_likes以(post_id,user_id)为主键，点赞/取消均幂等；不暴露点赞人名单。

互助榜提供北京时间本月与总榜，依次按已验收积分、完成次数、难度累计排序，三项相同并列；前100人之外仍能查看本人记录。姓名、部门和累计成绩可见，接取确认前明确说明；榜单不返回任务ID、匿名帖子归属或私密文件。已停用/删除账号从可见榜单隐藏，流水保留，恢复启用后继续统计。点赞本身不发积分。

## 迁移

初次启动新版本会将旧的未接取草稿/开放卡悬赏收敛到1～5并标记five-point-v1；已接取的旧约定、已完成任务和已发流水不回改。历史较大额度仅按原锁定约定结算，用户无法通过API伪造旧规则标记。不会为过去已完成但尚无流水的任务回溯发分。升级前用SQLite在线备份，连同uploads/care-media/official-media一并备份。

接口见API.md，端到端验证见VALIDATION.md。示例排名截图来自独立测试库，经真实发布、接取和验收接口生成合成记录，不会写入正式员工数据。
