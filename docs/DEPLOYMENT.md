# 互联网访问方案

当前只在本机运行，本文件是后续实施方案，没有创建公网入口、调整防火墙或部署网站。

## 比赛演示：本机加访问隧道

链路：受邀访问者 → HTTPS 域名与访问验证 → 隧道 → 本机 8787 的正式构建服务 → 本机私有 Dify。

1. 先完成下方“上线前需要修改的代码”，并确定访问范围。
2. 运行 `npm run build`，随后 `npm start`，以 8787 的单服务提供页面和接口。
3. 选择可从实际访问网络连通的隧道服务，例如 Cloudflare Tunnel；将受保护的公开域名路由到 `http://127.0.0.1:8787`。部署时依据服务商当前文档配置。
4. 给试用人员设置访问策略，再从另一张网络验证登录、建档、两轮 AI 澄清和发布。不要只验证首页能打开。
5. 本机、Docker、Dify、网站和隧道必须持续运行；电脑休眠、关机或网络中断会影响访问。

只发布网站入口即可。Dify 管理后台、数据库、插件服务以及模型密钥不需要公开给访问者。隧道不能代替项目的应用权限；当前公开公屏与自主注册的访问范围也需要明确决定。

Cloudflare Tunnel 使用出站连接，可在没有公网 IP、没有开放入站端口的情况下连接本地服务；公开主机名可配合 Access 限制访问人员。其具体可用性还需用参赛人员所在网络实测。

参考：[Tunnel 原理](https://developers.cloudflare.com/tunnel/concepts/)、[保护公开应用](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/self-hosted-public-app/)。

## 长期使用：服务器加域名

链路：浏览器 → HTTPS 域名 → Caddy/Nginx → 摸摸鱼 Node 服务 → 私有 Dify 服务。

实施顺序：

1. 准备持续运行的服务器与域名，按实际网站和 Dify 的资源需求选型。
2. 迁移项目、生产环境配置和业务数据，安装 Node.js 24；通过 `npm ci`、`npm run build` 构建，以 `npm start` 提供页面与 API。开发用 5173 端口不作为公网服务。
3. 部署 Dify，或通过受控的私有连接访问现有 Dify。**服务器中的 127.0.0.1 指服务器自身，不是当前办公电脑。** 如果 Dify 不与网站同机，需要修改 `DIFY_BASE_URL`。
4. 用 Caddy/Nginx 反向代理到本机 8787，并配置域名与 HTTPS。应用仍可只监听 127.0.0.1，公网由反向代理承接。
5. 使用系统服务或容器守护进程管理重启与日志；设置 Dify 超时所需的代理读超时；一致备份数据库、data/uploads 附件目录和 Dify 配置，并实际验证恢复。
6. 从外部网络验收整条业务链路，再向目标人员开放。

Caddy 可以为满足域名解析和网络条件的公开域名自动申请并续期 HTTPS 证书。参考：[Caddy 自动 HTTPS](https://caddyserver.com/docs/automatic-https)。

## 上线前需要修改的代码

以下是对当前项目实现的检查结果，不是已完成的功能。

| 当前实现 | 上线所需修改 |
| --- | --- |
| 写请求 Origin 只与 `http://Host` 比较 | 配置准确的公开 HTTPS origin；保留来源校验，不能简单删除；反向代理信任范围需明确 |
| 本机 HTTP 会话 Cookie | 生产 HTTPS 使用 Secure Cookie，并验证反向代理后的登录与退出 |
| 可自行注册，公屏允许未登录浏览 | 按实际目标改为受邀注册/公司身份认证，明确公屏是否仅登录员工可见 |
| 登录与模型调用没有生产限流配额 | 增加登录保护、每人 AI 调用限额、并发与成本限制 |
| SQLite 本地单文件存储 | 小规模可继续使用，但要做一致性备份；WAL 模式下不要只复制正在写入的主文件，使用 SQLite 在线备份或停服务后备份。多实例扩容前再评估数据库方案 |
| 手动打开窗口运行 | 改成开机启动、异常重启、日志与监控，并安排数据恢复验证 |

上传功能当前仅适用于受控本地试用；公网需增加总上传并发/速率限制、磁盘监控、恶意文件扫描与备份恢复策略。个人配额计原件，预览副本会额外占磁盘。

上线前还应核对内容管理、匿名权限与管理员职责。现已支持主账号和第二管理员、账号管理、公开内容治理与官方发布入口；上线前仍需确认实际职责与访问范围。

建议先做受控的演示访问，验证使用体验和模型成本，再按实际人数与使用强度做长期部署。

人员匹配启用后，需同时备份SQLite的matching_jobs/notifications以及.env中的独立Workflow密钥；迁移Dify时导入匹配DSL并发布，更新密钥和地址。后端常驻时自动运行待处理任务和15分钟补查，无需保持聊天窗口。停止网站期间不发送，重启补查。`MATCHING_SCHEDULER=off`只关周期唤醒，用户发布及档案更新仍即时入队。公网部署还需访问控制、任务量监控和调度唯一实例；目前未做企业级压力测试。

语义匹配版本还需备份心情角care_posts/care_comments/care_reports等表及私密对话；这些是敏感数据，限制备份访问。semantic_match_cache只存已验证的匹配决策，最长复用1小时。更换模型或匹配策略时递增DIFY_MATCHING_POLICY_VERSION使缓存失效。匹配与心情审核共用双分支Workflow，缺少配置时匹配明确回退标签规则，心情公开审核则返回503并保留未发布内容。生产上线前需要落实反馈处理人员、数据保留/删除方案和隐私告知；目前反馈仅记为待处理，没有人工值守承诺。详见[MATCHING.md](MATCHING.md)、[CARE.md](CARE.md)。
